# What nothing is watching

**Each of these is a gap in coverage, not a defect, and each needs a yes or a no.** Re-checked against the
tree on 2026-08-27. The five that had a known answer and no decision in them moved to the TODO list.

## The frozen OpenAPI copies on the docs site drift with nothing watching

`sites/docs/collections/_versions/*/swagger/*.json` are hand-placed copies. `tooling/openapi.just` writes
only to `artifacts/openapi`, and `tooling/regen.just check` - the recipe that exists to fail on generated
data drifting - lists six paths and none is a swagger folder. The docs deploy row in the release plan is the
only control.

## The instance page is the only v4 consumer that ships in the image

`api/src/Binacle.Net.UIModule/_js/instance.js:52` fetches `/api/v4/presets`; everything else in the module
and both site demos are on v3. `sites/www/pages/how-it-works.html:134` says v4 "can change in a patch
release. Do not integrate against it by accident."

**Do not move that line to v3 without reading `plans/api/uimodule-instance-presets.md` first.** That plan
deletes the file - the page would be rendered server-side and the fetch would not exist. Editing the call is
work it throws away. **This file owns the gap; that one owns the file.** The cheap answer while it is still
an idea is a design record saying why the image ships a v4 caller.

## `just regen check` runs nowhere, and two of its files cannot pass it

**No workflow calls it.** `grep -rn regen .github/workflows/` returns nothing, so the recipe that exists to
catch generated data drifting only ever runs when someone runs it by hand.

**And when it does run it fails, on `vipaq/test-vectors/interop/cs/{deflate,gzip}.json`.** Three of the
fourteen vectors in each file come back different - checked 2026-08-31 on .NET SDK 10.0.111. **It is not a
data problem.** The three are the ones large enough for deflate to compress rather than store, the new bytes
are shorter every time, and the ViPaq suites pass on both sets: 421 C# and 380 TypeScript against the
committed vectors, and the same numbers against the regenerated ones.

**The cause is that .NET's deflate output is not stable across runtime patch versions, and `global.json`
pins no SDK.** So the committed bytes record which SDK happened to be installed when someone last ran the
generator. Regenerating fixes it until the next SDK update, then it comes back.

**Three ways out, and they are not equal.** Commit the new bytes and accept it recurring. Pin the SDK in
`global.json`, which makes the check honest and constrains every build. Or compare what the vectors *mean*
rather than their bytes - decode and compare - which is what the interop suites already do and is the only
one that stops the question coming back.

## A skipped matrix job names itself `${{ matrix.site }}`

`pull-request.yml:93` sets `name: Site build (${{ matrix.site }})` over a matrix of `docs`, `demo`, `www`.
**A skipped job never has its matrix evaluated**, so the checks list prints the expression instead of the
site - and prints it twice for three sites, because identical names collapse. Seen on a real pull request,
2026-08-31.

**It costs nothing today and that is the trap.** `Gate` is the only required check and it reads job results,
not names, so nothing breaks. What is lost is the one thing the list is for: on a code-only change every site
job skips, and that is exactly when you want to read which ones skipped and why.

**Three answers.** Give the job a static `name: Site build` and let the matrix leg show in the run itself;
leave it and write down that the checks list is not the place to read a skip; or drop the expression only
from the name and keep it in the steps. **The first is one line.**
