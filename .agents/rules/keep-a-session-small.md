# Keep a session small

A big session listens worse. It loses the rules it read at the start, and "plain and short" goes first.

## Start small

Read the rules, the plan's main file and the one step file you are on. Not the whole folder. Open anything
else only when the step needs it.

## Warn him before it gets big

Stop and tell the maintainer in one line when:

- the step's work is done;
- the work has grown past what the step file says;
- you have read many large files or long outputs - run reports, a whole folder;
- the talk has run long, or you catch yourself reading something twice.

Say: "This session is getting big. Stop here and start a new one on <the next step>."

**The step file is the handoff.** Write the facts and open questions there. Do not write a prompt for him to
paste into the next session.

## Plan in pieces one session can finish

Split big work into step files. Each is work one session can finish from start to end. If a step cannot be
finished in one session, split it again.

## Why

Measured 2026-09-28 over a week of sessions on one plan. Each read the whole plan folder first, 80k to 120k
tokens before its first answer, and grew to 150k to 450k. The biggest are the ones where he said "too much",
"plain english" and "stop" the most. Prompts written by one session for the next carried its guesses in as his
words.
